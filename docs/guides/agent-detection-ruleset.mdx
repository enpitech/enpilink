Agent detection in enpilink is split into two halves on purpose: **methods** — the
algorithms ("no `Sec-Fetch-*` headers?", "title-cased client hints?", UA-regex
match, IP-CIDR lookup) — and **data** — the User-Agent patterns, IP ranges, header
signatures, and labels those methods consume. enpilink is **self-hosted software,
not a SaaS**, so *both halves ship with your instance*: the methods are the
package's logic, and the data is a versioned **ruleset your instance carries and
serves itself.**

The headline consequence: **detection works offline, out of the box, with no call
to enpitech.** A fresh install classifies `GPTBot`, `ChatGPT-User`, `Googlebot`,
and the rest immediately, from its own packaged ruleset — there is no enpitech CDN,
and nothing to fetch. This page explains that default, the distributed self-host
option, and why the whole thing is safe to run.

## The default: your instance's own packaged ruleset, in-process

By default (`agent.ruleset.url` empty), your instance loads its **own packaged
ruleset directly into memory at boot** — validated, version-stamped, no network
call. That is the sole default detection source, and it has three consequences:

- **Offline by construction.** There is no outbound request to make detection
  work, so an air-gapped or network-restricted deployment needs no special
  configuration — the data is already there.
- **Your instance also *serves* that exact ruleset** at
  `GET /__enpilink/agents/ruleset` — a public, keyless, one-directional endpoint
  (rules out; nothing about your traffic in). It is the same bytes it classifies
  with, so a distributed adapter can point at it and agree on the `version`.
- **Updating detection = updating your enpilink** (a new package version ships an
  updated ruleset), or re-publishing a ruleset you host yourself. There is **no
  central push** — nothing enpitech controls about your running instance.

<Note>
**Not a hidden fallback — the honest reconciliation.** The packaged ruleset is
the instance's *default source*, loaded through the normal validate → version →
backfill path. It is **not** a silent classifier fallback that kicks in behind a
configured remote URL: if you point `agent.ruleset.url` at a remote source and
that source fails, detection degrades to `pending` (loud, detectable) — it does
*not* quietly swap to the packaged data. Packaged is used precisely when you have
*not* configured a remote URL.
</Note>

## The distributed option: point an edge adapter at your own server

Sometimes the code that sees the request runs *separately* from your enpilink
server — a Cloudflare Worker, a Next.js edge middleware, a static site's edge.
Those runtimes have no packaged ruleset of their own (they are zod-free, edge-safe
bundles). To classify **at the edge**, point the adapter's `agent.ruleset.url` at
**your own enpilink server's** `/__enpilink/agents/ruleset` endpoint (or a mirror
you run) — never at enpitech. Then:

- The edge fetches the ruleset [stale-while-revalidate](#stale-while-revalidate-a-request-never-waits-on-the-fetch),
  caches it across isolates (KV / Cache API), and classifies in the request-path
  hop it already is.
- With **no** URL configured, the edge captures records `pending` and **your Node
  enpilink server classifies them on ingest** (it always has its packaged ruleset)
  — so you still get labelled data, just attributed by the Node side.

Either way, the ruleset only ever travels between *your own* services. There is no
configuration in which detection contacts enpitech.

## Stale-while-revalidate: a request never waits on the fetch

This matters only in the distributed case (the in-process default does no I/O at
all), and it is the non-negotiable latency law:

- Reading the current ruleset is a **synchronous field read** — an in-memory
  lookup, never a network call, on the request path.
- When a fetched ruleset is past its TTL, a refresh runs **in the background**
  (`waitUntil` on the edge, a deferred async task on Node). The request in flight
  is served from the **existing** ruleset and returns immediately.
- The fetch has a **hard timeout** (`agent.ruleset.timeoutMs`, default 5 s). A
  hung or slow source can never pin resources or delay anything — a timeout is
  just a failed refresh, and the last-good ruleset keeps serving.

<Note>
**The headline guarantee, stated plainly:** no request your server handles ever
blocks on a ruleset load — not the first one, not one during a refresh. The
in-process default reads memory; a distributed fetch happens off to the side.
</Note>

## Capture is independent: labels backfill

Capture and classification are **separate steps**, and only classification uses
the ruleset:

- **Capture always writes the raw row** — the request fingerprint (header order
  and casing), the hashed IP, timing, and outcome — regardless of ruleset state.
  You never lose a request because detection wasn't ready.
- **With no ruleset loaded yet** (a cold edge isolate before its first fetch, or a
  deployment that disabled the ruleset), rows land labelled **`pending`** (family
  and class are `null`). This is honest and distinct from a real `unknown` verdict
  — it means "not classified *yet*", not "not an agent."
- **Backfill** re-classifies pending rows the moment a ruleset loads. In the
  in-process default the packaged ruleset loads at boot, so this is effectively
  immediate; in the distributed case it labels any rows captured before the fetch
  landed.

## Content-addressed versions: a data change always re-classifies

The ruleset's `version` field is **content-addressed** — it embeds a hash of the
data (`<releaseTag>-<sha256(content)[:10]>`). This makes one guarantee structural:

- **A data change changes the hash → changes the version → triggers backfill
  re-classification** across your existing rows. When you update your enpilink (or
  re-publish a ruleset you serve), a rule fix propagates to historical data, not
  just new requests.
- Because the in-process ruleset and the served endpoint are built from the *same*
  corpus, they carry the *same* version — so a distributed adapter pointed at your
  server agrees on the version and does not needlessly re-classify.

## Fail-soft: detection never breaks a response

Whether in-process or distributed, detection can never turn a good page into an
error:

| Situation | What happens |
|---|---|
| In-process default | The packaged ruleset is always present — detection just works, offline, no I/O. |
| Distributed source slow | The in-flight request is served from the cached ruleset; the refresh times out in the background. No latency impact. |
| Distributed source down, cache warm | The last-good ruleset keeps classifying. |
| Distributed source down, cold isolate | The edge captures `pending`; your Node server backfills the labels. |
| A corrupt artifact is served | It fails schema validation and is **rejected** — the last-good ruleset stays live (or detection stays `pending`). A bad publish can't poison a running site. |

Your site **never breaks** on the ruleset. The worst case is *staler detection*
or *`pending` labels* — never a broken response.

## Air-gapped / self-host notes

- **The Node instance needs nothing.** Its packaged ruleset is already offline —
  there is no fetch to block and no URL to set.
- **To serve many distributed adapters from one file**, run `build:ruleset` to
  emit the static artifact and host it on *your own* static host / CDN, then point
  the adapters' `agent.ruleset.url` at it (see [`agentCapture` &amp; the
  ruleset](/api-reference/agent-ruleset#publishing-the-ruleset)). Never at
  enpitech.
- **To disable classification entirely** (pure capture, rows stay `pending` until
  you backfill), set `agent.ruleset.enabled=false`.

## Tuning freshness

The relevant `agent.ruleset.*` keys (all runtime-editable — see
[Configuration](/guides/configuration#agent-ruleset-keys)):

| Key | Default | What it does |
|---|---|---|
| `agent.ruleset.enabled` | `true` | Supply detection with a ruleset. Off → pure capture, rows stay `pending`. |
| `agent.ruleset.url` | *empty* | Empty → the instance's own packaged ruleset, in-process (offline, no network). Set it — only in the distributed case — to your own enpilink server's `/__enpilink/agents/ruleset` (or a mirror / `file://` path). |
| `agent.ruleset.ttlSeconds` | `0` | Distributed fetch only. `0` honors the artifact's `Cache-Control: max-age`; a positive value forces a local TTL. |
| `agent.ruleset.timeoutMs` | `5000` | Distributed fetch only. Hard fetch timeout. |
| `agent.ruleset.mode` | `live` | Distributed fetch only. `live` = long, centrally-controlled TTL; `dev` = short TTL to pick up a signature you're testing quickly. |

The **Detection ruleset** card on the Console **Agents** tab shows the live
version, last-refresh time, source (`packaged` for the in-process default, or
`network`/`cache` for a distributed fetch), mode, and TTL, and lets you edit mode
and TTL inline. It reads `GET /__enpilink/agents/ruleset/status`.
